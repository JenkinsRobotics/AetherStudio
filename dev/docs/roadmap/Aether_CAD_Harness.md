# Aether CAD harness workspace

Updated 2026-10-01. Owner: CAD product. **Initial editable demo; full feature parity remains open.**

Jonathan requested a center-workspace harness application with physical Layout and pin-to-pin Harness views, matching the supplied automotive diagrams. He subsequently expanded the target to the full public feature set documented at [harness.design](https://docs.harness.design/). The app itself uses Aether naming, shared UI and original connector artwork; research links belong in this developer document only.

## Launch and scope

Open **Aether CAD → Open harness demo**, or `/cad/index.html?demo=harness` on the Studio host. In standalone CAD development use `http://127.0.0.1:5173/?demo=harness` with the port printed by Vite. The UI showcase also links the demo under **Widgets → Panels → Electronics + instruments**.

The demo loads `Aether CAD/public/examples/harness-demo.json`: a twin-cylinder engine harness with 14 components, 16 wires and 21 physical bundles. It intentionally retains unused pins so review/authoring flows can be exercised. The file is a design study, not a validated vehicle harness. Housings and part numbers are generic, with zero initial prices.

The workspace uses `DocumentBar`, `WorkspaceRibbon`, `WorkspaceShell`, `TreePanel`, `DataTable`, `SettingsWindow`, shared fields, icons and theme controls. Presentation primitives (`HarnessConnectorCard`, `ConnectorFace`, `ConnectorPreview`, `HarnessConnectionTable`, `HarnessDrawingScope`) belong to `core/ui`; original housing art belongs to `core/assets/electronics`. Electrical connectivity, routing, document edits, validation and persistence belong to `Aether CAD/src/harness-demo/`. Neither the shared UI nor this demo imports the parked CAD engine to define harness behavior.

Layout and Harness are projections of one document. Physical bundle lengths are explicitly millimeters; drawing coordinates are layout units, **not manufacturing scale**. The Connections report derives wire lengths from the shortest continuous physical path. An unrouted conductor retains its explicitly marked manual length. The parts report derives wire usage in meters and connector usage in pieces. Changing a bundle length updates both reports. Moving schematic cards does not change physical lengths.

## Feature audit

Research covered 80 retrievable public documentation pages across components, views, parts and features. Three category-only URLs (`/part/accessory`, `/part/covering`, `/part/terminal`) returned 404; their individual child pages were available. This is a documentation audit plus the supplied visual references, not a verified walk-through of every interaction in the source application. No external source code, manufacturer catalog, brand artwork or project files were imported.

“Implemented” below describes this demo's behavior, not full equivalence. “Partial” identifies a real implementation with specific gaps. “Planned” means there is no working implementation to rely on.

## Implementation order and gates

1. **Durable product document.** Replace coordinate identity with explicit layout junction IDs, preserve graph adjacency through moving/splitting/merging, version the schema, and register harness documents in Studio storage. Add deterministic migrate/roundtrip/undo tests before promising project storage. The current local draft is shared by tabs on the same browser origin, not account-isolated host storage.
2. **Complete the authoring loop.** Multi-selection, nested groups, precise orthogonal route editing, arbitrary pin labels/counts, pin deletion/rewiring, selection framing, configurable live tables and real editable pinouts. Exercise the reference engine-bay example entirely from a blank document.
3. **Harness-specific parts.** Contact/accessory ownership, summed wire area, cables/shields/twists, coverings and terminal compatibility. Quantities must come from the document graph; no fabricated supplier data or cost estimates.
4. **Manufacturing outputs.** Physical-scale formboard, dimensional validation, printer calibration, PDF and spreadsheet exports. Compare exported route lengths and pin maps back to the source document. A screenshot/SVG alone does not meet this gate.
5. **Suite services.** Server revisions, sharing/team libraries, external catalogs, subharnesses and agent tools. Announce contracts and coordinate Python host work with its owner; keep harness domain logic product-owned.
6. **Parity acceptance.** Each audit row needs an interaction test plus a saved/reopened project, light/dark inspection and appropriate export evidence. Mark the full request complete only after all rows have equivalent behavior or Jonathan explicitly changes the scope.

## Verification and known limits

Current evidence is recorded in `dev/docs/reality/STATUS.md` and the active briefing. Model regression tests live in `Aether CAD/src/harness-demo/model.test.ts`; real Chrome authoring tests live in `aether-map/e2e/cad-harness.spec.ts` because that package already supplies an isolated Studio test host. This does not make Map an owner of harness logic.

No simulation, electrical safety certification, physical connector fit, supplier availability, cloud collaboration, interoperability or complete reference-product parity is claimed. Source screenshots and export review test the initial demo only.
